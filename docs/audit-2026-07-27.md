## Architecture réelle

L’application est un site statique :

- `index.html` : structure, métadonnées, CSP, dépendances et composants accessibles ;
- `app.js` : IIFE unique, état en mémoire, appels réseau, calculs, Leaflet et interactions ;
- `style.css` : responsive, thèmes et composants ;
- `partage/index.html` : page sociale autonome ;
- `assets/` : manifeste, icônes et aperçus sociaux ;
- `validation/mission2-browser.cjs` : banc fonctionnel CDP sans dépendance npm ;
- `validation/refresh-performance.cjs` : banc de performance CDP ajouté par cet audit.

Leaflet 1.9.4 est chargé depuis jsDelivr avec SRI. Inter et Material Symbols sont
chargés depuis Google Fonts. La carte utilise les tuiles OpenStreetMap. Il n’existe
ni framework, ni gestionnaire de paquets, ni compilation, ni backend, ni compte,
ni publicité, ni tracking, ni analytics.

## Problèmes retenus

### Important — calculs redondants dans le regroupement

- preuve : 115,82 ms de CPU métier et intervalle de frame de 116,7 ms ;
- scénario : 2 593 détections denses, reproductible par le banc ;
- cause : les couples déjà reliés dans la même composante Union-Find étaient
  recalculés avec distance géographique ;
- impact : tâche longue et gel perceptible après la réponse FIRMS ;
- correctif : ignorer uniquement les couples dont les racines Union-Find sont
  déjà identiques ;
- risque : faible, la composante est déjà prouvée connectée ; aucun seuil ni
  résultat métier n’est changé ;
- validation : suite fonctionnelle complète et profil avant/après.

### Important — actualisations redondantes lors de changements rapides

- preuve : 18 requêtes et 1,31 Mio pour trois changements synchrones ;
- cause : chaque événement `change` lançait immédiatement une actualisation
  complète ;
- impact : quota FIRMS consommé, trafic et annulations inutiles ;
- correctif : regroupement sur 120 ms uniquement pour rayon/période ;
- risque : léger délai après le dernier changement ; les actions manuelles,
  villes, clés et actualisations automatiques restent immédiates ;
- validation : une seule série de 6 requêtes et test navigateur dédié.

### Amélioration mesurable — cache Overpass sans borne

- preuve : `localityCache` conservait chaque résultat résolu sans TTL ni maximum ;
- impact : croissance potentielle lors d’une longue session multi-zones, chaque
  réponse pouvant atteindre la limite client de 8 Mio ;
- correctif : LRU de 8 trajets, TTL 30 min, requêtes pendantes non dupliquées ;
- risque : un ancien détail peut refaire un appel après éviction ;
- validation : dix trajets distincts, dernier réutilisé, premier évincé.

### Non-problèmes vérifiés

- zoom et déplacement répétés : 0 appel FIRMS, météo ou AQI ajouté ;
- réponses obsolètes FIRMS, météo, Nominatim et Overpass : neutralisées par
  identifiants et annulation ;
- échec d’une source FIRMS : autres sources conservées ;
- météo, AQI et localités indisponibles : FIRMS reste exploitable ;
- couches après session longue : stables ;
- architecture sans build : aucun bénéfice démontré à une modularisation dans
  cette mission ;
- aucune dépendance ou abstraction supplémentaire justifiée.

## Compatibilité, limites et rollback

Confirmé :

- URL, point d’entrée, page de partage et manifeste inchangés ;
- stockage historique et préférences inchangés ;
- données existantes non migrées et non effacées ;
- thèmes et responsive inchangés ;
- déploiement toujours statique ;
- aucune dépendance, compilation, télémétrie ou infrastructure ajoutée.

Limites restantes :

- disponibilité, latence et quotas des services externes ;
- AQI modélisé, pas une mesure locale ;
- trajectoires de fumée pédagogiques, pas un modèle de dispersion ;
- très grands jeux de points toujours rendus par Leaflet, même si le gel de
  regroupement mesuré est supprimé ;
- `app.js` et `style.css` restent volumineux ; aucune extraction n’a été
  justifiée par cette correction ciblée ;
- essai lecteur d’écran matériel non disponible.

Éléments volontairement non modifiés :

- seuils métier, rayon, périodes et sources ;
- représentation cartographique et vocabulaire ;
- endpoints, tuiles, polices et algorithme de trajectoire ;
- architecture sans build ;
- production et `main`.

Rollback avant fusion : fermer la PR et supprimer uniquement sa branche distante.

Rollback après une fusion éventuelle : ouvrir une PR qui réverte, dans l’ordre
inverse, les commits de cette branche. Le retour arrière ne demande aucune
migration de stockage. Vérifier ensuite les SHA-256 servis par GitHub Pages.
